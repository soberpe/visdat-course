# What is actually wrong with the data

<div class="boxes">
<div><b>Gaps</b>The logger dropped samples. The time column has holes you will not see in a plot.</div>
<div><b>Units</b>Degrees or radians, bar or pascal, g or m/s². Nobody wrote it down.</div>
<div><b>Drift</b>The sensor has an offset that changes over the run.</div>
<div><b>Outliers</b>A spike. Is it a fault, or is it the event you are looking for?</div>
</div>

<p class="note">Every one of these is invisible in <code>df.head()</code>. You have to go looking.</p>

# First contact

```python
import pandas as pd

df = pd.read_csv("data/motorcycle_ride.csv")
print(df.shape)
df.head()
df.info()          # dtypes and missing values
df.describe()      # min, max, mean, quartiles
```

Read the output together. What is suspicious?

<!--
describe() is the step that is easiest to skip and most expensive to skip.
Three numbers in it are wrong, and none of them is a measurement:

- coolant_c has a minimum of -40. That is what the sensor sends before it is
  ready, a placeholder, not a temperature.
- brake_front_bar has a maximum of exactly 409.5. That is the top of a 12 bit
  converter (4095 times 0.1 bar), a loose connector.
- speed_kmh has a maximum of exactly 255. The largest value one byte can hold,
  an error frame from the bus.

In each case, "exactly" is the suspicious word. Real measurements are rarely
round, placeholders and limits always are. The count row and info() show the
second problem: three columns have fewer values than the others.

Reading describe() critically is the actual skill here.
-->

# Every figure has the same three parts

<div class="boxes">
<div><b>Figure</b>The page. Holds everything, controls size and saving.</div>
<div><b>Axes</b>One coordinate system. A figure can hold several.</div>
<div><b>Artist</b>Everything you see: lines, text, ticks, the legend.</div>
</div>

```python
fig, ax = plt.subplots(figsize=(8, 4))   # one Figure, one Axes
line, = ax.plot(t, a_z)                  # an Artist
ax.set_xlabel("Time [s]")
```

<p class="note">Know which of the three you are holding, and every example in the documentation becomes readable.</p>

<!--
This is the single most useful idea of the 2D part. A question to check it:
in `plt.plot(...)`, which of the three are you addressing? None explicitly.
pyplot picks one for you, which is exactly the problem.
-->

---

# Two APIs, one rule

<div class="cols">
<div>

**pyplot**, stateful

```python
plt.plot(t, a_z)
plt.xlabel("Time [s]")
plt.show()
```

Short. Fine in a notebook, while exploring.

</div>
<div>

**Object oriented**, explicit

```python
fig, ax = plt.subplots()
ax.plot(t, a_z)
ax.set_xlabel("Time [s]")
```

Says what it acts on. Use it in scripts.

</div>
</div>

> The rule: pick one per file. Mixing them is where the confusing bugs come from.

# Which plot answers which question

| The question | The plot |
|---|---|
| How does it develop over time? | Line |
| Do these two quantities relate? | Scatter |
| How is this distributed? | Histogram |
| How do the categories compare? | Bar |
| Where is the outlier? | Scatter, or a box plot |

<p class="note">Start from the question, not from the chart menu.</p>

# Is the sampling rate really constant?

```python
dt = df["timestamp"].diff()
nominal = dt.median()
gaps = dt[dt > 2 * nominal]

print(f"nominal rate: {1 / nominal:.0f} Hz")
print(f"gaps:         {len(gaps)}, longest {gaps.max():.2f} s")
print(f"jitter:       {dt[dt <= 2 * nominal].std() * 1e6:.0f} µs")
```

> Everything downstream assumes even spacing: filters, FFT, integration. If the
> spacing is uneven and you do not know it, every result after this point is
> wrong by an amount nobody can estimate.

<!--
The file has seven gaps. Six are a few samples long, one is more than a second,
the logger stalled while writing to its memory card. None of them is visible in
a plot of the speed, because the line simply connects across the hole.

Why the jitter is computed without the gaps: one gap of a second would dominate
the standard deviation and make a jitter of 0.2 ms look like milliseconds.
-->

---

# Missing values: three strategies, three assumptions

```python
df["coolant_c"].ffill(limit=300)       # hold the last value, 3 s at most
df["lean_deg"].interpolate(limit=20)   # assume a smooth change, 0.2 s at most
df.dropna()                            # give up on the row
```

<div class="boxes">
<div><b>Forward fill</b>Right for a slow signal like the coolant, wrong for a step like the throttle.</div>
<div><b>Interpolate</b>Right for a smooth quantity like the lean angle, wrong across a real gap.</div>
<div><b>Drop</b>Honest, but it changes your time spacing.</div>
</div>

<p class="note">Whatever you choose, write down which one and why. That sentence belongs in your README.</p>

<!--
The limit is the decision in disguise. The coolant sensor only updates once a
second anyway, so holding its value for three seconds is defensible. Holding
the lean angle for three seconds in the middle of a bend is not.

None of the three lines changes df, each returns a new object. This is the
point about references from the programming basics: assign the result, or
nothing happened.

An open question to try yourself: what should the throttle column get? It has
two gaps of a few tenths of a second, and a throttle can jump in that time.
-->

# Outliers

```python
def iqr_outliers(s):
    q1, q3 = s.quantile([0.25, 0.75])
    fence = 1.5 * (q3 - q1)
    return (s < q1 - fence) | (s > q3 + fence)

iqr_outliers(df["speed_kmh"]).sum()   # the error frames
iqr_outliers(df["lean_deg"]).sum()    # every bend of the ride
```

> The method finds points that are unusual. It cannot tell you whether they are
> faults or findings. On the lean angle it flags every bend, because riding
> upright is what is usual.

<p class="note">Never delete silently. Mark, count, and report how many you removed.</p>

<!--
Run iqr_outliers on accel_x as well. Around 145 s the bike brakes from
100 km/h to walking pace at close to 1 g, a deer on the road. It is flagged,
together with every other firm braking and acceleration. A script that dropped
outliers automatically would have deleted the most important seconds of the
ride.

In practice this happens more often than one would think: measurements in
which the "outliers" were the only real content.
-->

# Time as an index

```python
df["datetime"] = pd.to_datetime(df["timestamp"], unit="s")
df = df.set_index("datetime")

df.resample("100ms").mean(numeric_only=True)   # downsample
df["accel_x"].rolling("1s").mean()             # smooth over a window
df["accel_x"].rolling("1s").std()              # noise over a window
```

With a time index, pandas understands windows in seconds instead of rows, and
uneven spacing stops silently corrupting your averages.

---

# Smoothing costs something

```python
df["accel_smooth"] = df["accel_x"].rolling(window=50, center=True).mean()
```

<div class="cols">
<div>

**You gain**

Less noise, a readable curve, stable derivatives.

</div>
<div>

**You pay**

Edges get cut, real peaks get shorter, fast events disappear entirely.

</div>
</div>

<p class="note">Always plot raw and filtered together, at least once, before you trust the filtered one.</p>

<!--
Worth trying: zoom into the emergency stop around 145 s and plot accel_x
against accel_smooth. Then make the window 300 samples and watch the peak
deceleration shrink. Nothing about the brake changed, only the filter.
-->

---

# Calibration is subtraction, with a decision in it

```python
at_rest = df["timestamp"] < 15             # bike standing, engine idling
baseline = df.loc[at_rest, "accel_x"].mean()
df["accel_x_cal"] = df["accel_x"] - baseline
```

The code is trivial. The decision is not: those first 15 seconds have to be a
state you can defend as zero.

<!--
The baseline comes out at about 0.25 m/s². Two questions decide whether it
can be trusted. Does the idling engine matter? It adds noise, but no mean. Was
the bike standing on a slope? Then gravity adds a real component, and the
baseline would remove it wrongly.
-->

---

# Integration, and what it does to your error

```python
import numpy as np

dt = df["timestamp"].diff().fillna(0)

df["vel_x"] = np.cumsum(df["accel_x"] * dt)   # acceleration → velocity
df["pos_x"] = np.cumsum(df["vel_x"] * dt)     # velocity → position
```

> A constant offset in acceleration becomes a linear error in velocity and a
> quadratic error in position. That is why the IMU workshop asks you to walk a
> measured distance and compare.

# Why does this stress plot lie to you?

<p>Every FE postprocessor shows you rainbow colours by default.</p>

<!--
Worth a moment before reading on. The answer: rainbow is not perceptually uniform. Equal
steps in stress become unequal steps in perceived colour, so the yellow-green
band reads as a sharp edge where the field is smooth, and real gradients in the
red end disappear. People find "hot spots" that are artefacts of the palette.
-->

---

# Colour maps

<div class="cols">
<div>

**Avoid**

`jet`, `rainbow`, `turbo`

Perceptually uneven, invents edges, unreadable in grayscale, hard with colour
vision deficiency.

</div>
<div>

**Use**

`viridis`, `cividis` for magnitudes
`coolwarm` for deviation from zero

Perceptually uniform: equal data steps look like equal colour steps.

</div>
</div>

```python
ax.pcolormesh(X, Y, stress, cmap="viridis")
```

<p class="note">A diverging map only when zero means something, for example tension against compression.</p>

<!--
The same rule comes back in session 6, on a real stress field in 3D.
-->

---

# Before you show a figure to anyone

- Both axes labelled, **with units**
- A scale the reader can trust: does the y axis start at zero, and should it?
- More than one series: a legend, or direct labels
- Readable when printed in grey
- The file saved by the script, not by a screenshot

<!--
This is the checklist for the motion tracking assignment too. "The script
saves the figure" is what makes a result reproducible. A screenshot of a plot
is the visualization equivalent of typing results into a Word file by hand.
-->

# Storage

## When the CSV stops being a good idea

---

# Formats, and what each is for

| Format | Good at | Falls over when |
|---|---|---|
| **CSV** | Anything can read it | Large files, types, structure |
| **Excel** | Colleagues open it | Row limits, silent type changes |
| **HDF5** | Large arrays, fast partial reads | You want to open it by hand |
| **Parquet** | Columnar analysis, compression | Row-wise access |

<p class="note">CSV is a good interchange format and a bad working format. Both things are true.</p>

---

# HDF5 in practice

```python
# write, with a column you can query
df.to_hdf("data/motorcycle_ride.h5", key="ride01", format="table",
          data_columns=["timestamp"])

# read only what you need, without loading the file
part = pd.read_hdf("data/motorcycle_ride.h5", key="ride01",
                   where="timestamp >= 60 & timestamp < 120")
```

One file can hold many runs under different keys, with metadata, and you read a
slice of it without touching the rest.

# Compare it yourself

```python
import time
ride = pd.read_csv("data/motorcycle_ride.csv", dtype={"ride_mode": "category"})
big = pd.concat([ride] * 20, ignore_index=True)    # three hours of riding
big.to_csv("ride_3h.csv", index=False)
big.to_hdf("ride_3h.h5", key="ride", format="table")

t = time.perf_counter(); pd.read_csv("ride_3h.csv")
print(f"CSV, all     {time.perf_counter() - t:.2f} s")
t = time.perf_counter(); pd.read_hdf("ride_3h.h5", "ride")
print(f"HDF5, all    {time.perf_counter() - t:.2f} s")
t = time.perf_counter(); pd.read_hdf("ride_3h.h5", "ride", where="index < 6000")
print(f"HDF5, 1 min  {time.perf_counter() - t:.3f} s")
```

<!--
Numbers on your own machine beat any claim on a slide. Run it twice: the
second run reads from a warm cache, and a fair measurement says so.

The nine minute ride alone is too small to show anything, which is why the
first lines make three hours of it. Writing the CSV takes several seconds,
which is part of the lesson.

What to expect on a laptop: HDF5 reads the whole file about three times
faster, and one minute out of three hours comes back in a few hundredths of a
second. A CSV is text, and every number has to be parsed from its characters.
HDF5 stores the bytes the way they sit in memory.

The dtype argument in the first line matters more than it looks. Without it,
ride_mode stays a column of Python strings, and HDF5 loses most of its lead:
text is slow in every format. As a category, it is stored as small integer
codes, which is the same trick as on the memory slide.

Then look at the file sizes. Here the HDF5 file is larger than the CSV,
because the logger writes short numbers like 0.0, and in binary every float64
takes 8 bytes. complevel=5 in to_hdf shrinks the file to about a third, but
reading it is then slower again. Speed or size: compression is a trade, not a
free improvement.
-->

---

# Memory: the cheapest optimisation you will ever make

```python
df["ride_mode"] = df["ride_mode"].astype("category")
df["accel_x"] = df["accel_x"].astype("float32")

print(df.memory_usage(deep=True).sum() / 1e6, "MB")
```

float64 to float32 halves the memory and is almost always enough for sensor
data. A repeated string column as `category` can save 90 percent.

# Recap

- Look for **gaps, units, drift and outliers** before you compute anything
- Cleaning is a **decision**, so write down which one you made
- A figure is **Figure, Axes, Artist**. Know which one you are holding.
- The plot follows from **the question**, not from the menu
- Integration turns a small offset into a **large error**
- **Perceptually uniform colour maps**, labels with units, saved by the script
- CSV to exchange, **HDF5 to work**
